## 1. 文档目的

这份文档用于统一当前项目的产品范围、技术边界、上线标准、阻断风险与后续迭代方向。

## 2. 产品定位

本产品是一个面向新高考英语写作提分场景的垂直学习工具，不是泛聊天机器人，也不是单纯的范文生成器。

核心价值：

- 写前知道怎么下笔
- 写后知道为什么丢分
- 长期知道自己总是丢在哪里

当前产品心智：

- 主打：作文陪练
- 主打：严格批改
- 主打：个人提分档案
- 弱化：范文生成

## 3. 用户、地区与题型覆盖

### 3.1 V1 核心用户

- 高中生
- 新高考地区考生
- 英语作文基础薄弱、希望快速提分的学生

### 3.2 V1 非核心但可兼容用户

- 家长查看结果
- 老师辅助看学生弱项

### 3.3 V1 角色策略

V1 不做复杂多身份切换。

当前统一按“学生端”设计：

- 一个登录身份
- 一个训练入口
- 一个历史记录体系
- 一个提分档案体系

后续如果新增教师版或家长版，应单独扩展页面权限与数据视图，不直接在现有学生主链路里硬塞多角色判断。

### 3.4 首发地区覆盖边界

V1 首发只承诺覆盖以下写作题型组合：

- 应用文
- 读后续写

当前不承诺支持：

- 概要写作
- 非上述题型的地区卷变体

因此在产品文案、提审说明和用户提示中，必须显式写明：

- 当前版本主要面向“应用文 + 读后续写”地区
- 暂不支持概要写作省份的完整评测链路

如果未来进入概要写作省份，需新增：

- 概要写作题型识别
- 概要写作专属陪练模板
- 概要写作专属批改维度

## 5. 技术架构与当前环境

### 5.1 当前正式架构

`微信小程序 -> HTTPS 域名 -> Nginx -> Spring Boot 后端 -> Supabase PostgreSQL -> 大模型 / OCR`

关键原则：

- 所有敏感密钥只存在服务端
- 小程序只拿业务接口，不直接接模型厂商
- OpenID、JWT、试用次数、历史记录、订阅状态都由后端统一管理

### 5.2 当前模型供应商配置

当前项目已接入的是“OpenAI 兼容接口”形态的大模型网关，现阶段默认使用：

- 供应商：智谱
- 模型：`GLM-5.1`
- 接入方式：OpenAI-compatible

说明：

- 这是当前环境配置的默认路线
- 后端保留了替换模型供应商的能力
- 未来可切到 DeepSeek / 通义 / Kimi 等兼容接口，但必须先重新跑成本与质量评估

### 5.3 当前数据库配置

当前主路线数据库是：

- Supabase PostgreSQL

兼容说明：

- 代码仍保留 MySQL fallback 兼容能力
- 但正式路线不再以 MySQL 作为主存储方案

### 5.4 当前架构的现实限制

当前这套架构在工程上可跑通，但有一个必须单独确认的现实约束：

- 如果 Supabase 项目位于境外，则公开面向未成年学生上线前，必须先完成数据出境合规确认

如果无法完成该确认，V1 生产环境必须切回：

- 境内合规数据库
- 或其他经法务确认可用的数据存储方案

## 6. 核心业务模块

### 6.1 首页

首页承担三个职责：

- 让学生一眼知道当前最该做什么
- 展示试用状态
- 展示提分档案进度

首页当前结构：

- 顶部主卡片
- 试用额度卡
- 个人提分档案卡
- 工作模式卡
- 题型与目标档次选择
- 输入区与提交入口

首页体验要求：

- 视觉柔和，不走强工具感
- 行间距和卡片留白更适合长时间阅读
- 主按钮层级清晰
- 不保留功能重复但路径相同的双按钮

### 6.2 作文陪练

作文陪练不是直接代写整篇，而是写前或写中指导。

输入支持：

- 手动输入题目
- OCR 拍照识题
- 粘贴补充材料
- 填写补充要求

用户可选配置：

- 题型：应用文 / 读后续写
- 目标档次：进阶 / 学霸 / 满分
- 陪练阶段：写前 / 写中 / 写后
- 陪练模式：审题拆题 / 列提纲 / 弱项特训 / 分流建议

输出要求：

- 必须先判断用户当前处于写前、写中还是写后
- 必须贴合题型，不可混用应用文与续写逻辑
- 必须先检索结构化知识库，再生成指导
- 必须输出可直接下笔的中文指导
- 必须给出结构化骨架，而不是空泛建议
- 必须告诉用户下一步是继续练、直接下笔，还是转去严格批改

固定输出内容建议：

- 审题结论
- 要点拆解
- 开头怎么起
- 中段怎么承
- 结尾怎么收
- 本题必写
- 易失分点
- 可借用表达
- 下一步建议

### 6.3 严格批改

严格批改只处理“已有作文”，不负责从零新写一篇。

输入支持：

- 手动粘贴作文
- OCR 拍照识文
- 读后续写时补充原文材料和段首句

输出必须严格按四个固定部分：

1. 硬性指标初筛
2. 分项诊断与保守估分
3. 逐句无情诊断
4. 高分级整篇修改稿

批改要求：

- 所有判断必须基于学生原文证据
- 应用文优先看任务完成、身份、语气、得体性
- 读后续写优先看贴合原文、段首句承接、线索回收、人物逻辑
- 保守估分，不浮夸抬分
- 改写时尽量保留学生原有立意、结构和情节
- 如果续写缺少原文材料，只能做有限诊断，不能假装自己能完全判断贴题性

当前批改结果应覆盖：

- 内容
- 结构
- 语言
- 亮点
- 失分点
- 二稿提升
- 整篇提分稿

### 6.4 个人提分档案

提分档案是首页长期留存价值的核心，不是装饰卡片。

目标：

- 让学生看到稳定弱项
- 让学生知道下一阶段最该补什么

当前应支持：

- 最近样本数
- 高频失分维度
- 弱项标签
- 下一步提分重点
- 最近一次严格批改的联动入口

画像维度至少包括：

- 内容
- 结构
- 语言
- 亮点
- 失分点

冷启动要求：

- 新用户没有历史时，卡片不能留白
- 必须显示空状态文案
- 必须明确引导“先做 1 到 2 次严格批改”

当前状态：

- 已实现基础冷启动空状态

### 6.5 OCR

支持两个主场景：

- 拍照识题
- 拍照识文

要求：

- 识别后自动回填
- 失败时保留已识别成功的文本
- 前端提示区分“完全失败”和“部分识别成功”
- 只在用户主动点击 OCR 按钮时申请权限

新增强制要求：

- OCR 结果在进入“严格批改”前，必须允许用户人工确认与编辑
- 不允许“识别后不经确认直接送模”

要处理的不是只有“识别失败”，还包括：

- 识别错字
- 手写错判
- 段落错位
- 标点与换行错乱

### 6.6 历史记录

支持：

- 查看历史任务
- 按模式筛选
- 按题型筛选
- 查看结果详情

历史记录需要能还原：

- 原始输入快照
- 陪练骨架
- 批改分析
- 词数
- 时间
- 状态

## 7. 题型、档次与模式体系

### 7.1 题型

### 7.2 目标档次

- 建议密度

### 7.3 陪练模式

- 审题拆题

- 分流建议

## 8. 陪练知识库与 RAG 要求

作文陪练不能完全依赖大模型自由发散，必须挂载结构化知识库。

当前知识库要求：

- 先检索最匹配模板
- 再生成陪练结果
- 若模型输出不符合骨架，后端应拦截并重写或降级

`coach_template` 至少包含字段：

- 题型
- 场景
- 任务目的
- 官方阅卷逻辑
- openingStrategy
- bodyStrategy
- endingStrategy
- mustInclude
- riskPoints
- suggestedExpressions
- triggerKeywords

首版模板策略：

- 不追求几百条
- 先做 20 到 50 条高频模板
- 先覆盖应用文与续写高频场景

## 9. 账号、权限与用户管理

### 9.1 登录链路

- 小程序 `wx.login`
- 后端向微信换取 `OpenID`
- 绑定 `OpenID -> user_id`
- 下发 JWT

### 9.2 用户管理要求

- 同一用户重复登录不能产生脏重复绑定
- 并发首登时要能兜住唯一约束冲突
- 用户试用次数、历史记录、订阅状态都必须跟用户身份绑定

### 9.3 反薅羊毛边界

OpenID 是当前试用体系的主绑定锚点，因此以下行为不应重新发放试用额度：

- 换手机登录同一微信
- 卸载重装小程序
- 清缓存后重新进入
- 同一微信账号在不同设备登录

当前要求：

- 试用额度跟 `user_id / open_id` 绑定
- 不跟本地缓存绑定

后续可扩展：

- 设备指纹辅助风控
- IP / 设备频控
- 分享奖励或邀请奖励

当前状态：

- 生命周期试用绑定已实现
- 裂变奖励机制未实现

## 10. 成本与商业模型

这是 V1 公开上线前的 P0 章节。

### 10.1 为什么这是头号风险

本产品每次核心动作都会消耗模型资源：

- 作文陪练
- 严格批改
- OCR 识别
- 知识库检索补充 prompt

因此免费用户不是“零边际成本用户”，而是“每次调用都在烧钱的用户”。

### 10.2 当前模型路线

当前默认模型路线：

- 主模型供应商：智谱
- 主模型：GLM-5.1
- 接口方式：OpenAI-compatible

可替换候选：

- DeepSeek
- 通义
- Kimi
- 其他兼容接口模型

但任何切换都必须重新跑：

- 单次 token 成本测算
- 输出质量回归
- 故障率与延迟验证

### 10.3 上线前必须补齐的单次成本表

下表必须在公开上线前填完，不能空着：

| 动作 | 使用模型 | 预估输入 token | 预估输出 token | OCR / RAG 附加 token | 单次成本 | 是否已实测 |
| --- | --- | ---: | ---: | ---: | ---: | --- |
| 作文陪练 | GLM-5.1 | 待填写 | 待填写 | 待填写 | 待填写 | 否 |
| 严格批改 | GLM-5.1 | 待填写 | 待填写 | 待填写 | 待填写 | 否 |
| OCR 识题 | 待填写 | 待填写 | 待填写 | 待填写 | 待填写 | 否 |
| OCR 识文 | 待填写 | 待填写 | 待填写 | 待填写 | 待填写 | 否 |

### 10.4 成本测算公式

至少要测清：

- 单次陪练成本
- 单次批改成本
- 一个 5 次试用用户的平均模型成本
- 加上服务器、数据库、带宽后的总服务成本

建议采用以下口径：

- 单用户试用成本 = 5 次成功任务成本总和
- 免费用户池总成本 = 有效试用人数 × 单用户试用成本
- 付费回本率 = 免费用户池总成本 / 付费用户可贡献毛利

### 10.5 试用次数是否合理

当前规则是：

- 每用户总共 5 次体验

但这是“产品策略值”，不是“天然合理值”。

上线前必须根据成本表重新判断：

- 如果单次批改成本偏高，应考虑把试用从 5 次下调到 3 次
- 如果转化率偏低，应缩短烧钱窗口期
- 如果支付继续延后，试用次数应更加保守

### 10.6 支付未上线时的现金流判断

当前状态是：

- 真实支付未上线
- 试用用完后，用户暂时无法直接购买

因此这段时间本质上是“纯烧钱窗口”。

上线前必须明确：

- 这段窗口最多持续多久
- 可接受的总亏损上限是多少
- 如果超出上限，是否立即关闭新用户试用入口

### 10.7 限流与频控要求

除了总量试用，还必须增加频控设计：

- 单用户同一时刻仅允许 1 个处理中任务
- 单用户应有日频次上限
- 单设备 / 单 IP 应有异常调用监测

建议 Beta 期默认策略：

- 生命周期总额度：5 次
- 单日成功任务上限：2 次
- 同时处理中任务：1 个

当前状态：

- 生命周期总额度已实现
- 重复请求幂等已实现
- 单日频次上限未实现，属于上线前待补项

## 11. 未成年人合规、内容安全与数据治理

这是 V1 公开上线前的 P0 章节。

### 11.1 未成年人合规边界

目标用户大量是未成年人，因此不能只靠“隐私政策已上传”来完成合规。

必须单独回答：

- 是否涉及 14 周岁以下用户
- 如果涉及，监护人同意机制怎么做
- 敏感信息最小化采集是否成立

当前要求：

- 面向未成年人时，必须有独立的未成年人使用说明
- 涉及 14 周岁以下用户信息处理时，必须补监护人同意机制

当前状态：

- 文案类隐私文件已补齐
- 监护人同意机制未实现，属于公开上线前阻断项

### 11.2 内容安全链路

必须对以下内容做安全检查：

- 用户输入文本
- OCR 识别出的文本
- 模型输出文本

要求：

- 输入前置检查
- 输出后置检查
- 违规时不给模型继续执行或不给结果落地

拦截后的用户体验必须明确：

- 告知“当前内容无法处理”
- 不暴露敏感风控原因
- 不扣试用次数
- 给出修改建议或重试建议

### 11.3 数据出境风险

当前数据库主路线是 Supabase PostgreSQL。

若项目实例位于境外，则作文内容、账号标识等数据存在数据出境风险。

公开上线前必须二选一：

- 完成法务对数据出境的合规确认
- 或切换到境内合规存储

在未确认前，不能把“面向未成年学生公开上线”视为可直接执行事项。

### 11.4 数据留存、删除与注销

必须具备至少以下机制：

- 用户请求删除历史作文记录
- 用户请求删除个人账号关联数据
- 明确数据保留周期

## 12. AI 质量、估分准确性与评测集

这是 V1 公开上线前的 P0 章节。

### 12.1 为什么必须前置

“严格批改 + 保守估分”是核心卖点。

如果估分与真实结果偏差太大，用户口碑会直接受损，因此它不能被放到第三阶段再处理，必须在上线前建立基线。

### 12.2 评测集要求

V1 上线前至少准备：

- 20 道应用文题
- 20 道读后续写题
- 20 篇已有批改样本
- 尽可能引入真实或权威评分参照

### 12.3 估分质量门槛

V1 上线前必须定义并验证以下指标：

- 应用文估分平均绝对误差
- 续写估分平均绝对误差
- 结构化输出完整率
- 错判率

建议验收线：

- 应用文估分平均绝对误差不高于 1.5 分
- 续写估分平均绝对误差不高于 2.5 分
- 结构化输出完整率不低于 95%
- 严重错判率低于 5%

说明：

- 这是产品验收门槛，不代表官方评分准确率承诺
- 如达不到阈值，必须下调对外宣传口径，不能直接主打“严格批改”

### 12.4 上线前结论要求

在对外发布前，必须产出一份内部结论：

- 当前模型是否达到可用批改水位
- 哪些题型更准
- 哪些题型只能给“训练参考”，不能强承诺

当前状态：

- 批改结构与输出格式已定
- 正式评测基线未补齐，属于阻断项

## 15. 并发、重复请求、幂等与可用性

### 15.1 重复请求与幂等

这是已经落地的关键能力。

目标：

- 防止用户连续点按钮造成重复生成
- 防止网络重试造成重复扣次
- 防止同一请求重复写入多条历史记录

当前方案：

- 前端每次提交生成 `clientRequestId`
- 后端按 `user_id + clientRequestId` 做唯一幂等识别
- 第一次请求进入 `PROCESSING`
- 同一请求重复进来时：
- 若原任务已成功，直接复用结果
- 若原任务处理中，返回冲突提示
- 若原任务失败，提示用户重新发起新请求

对应约束：

- 数据库表 `essay_record` 新增 `client_request_id`
- 数据库唯一索引约束 `(user_id, client_request_id)`
- 前端加载中按钮禁用
- 传输异常重试时复用同一个 `clientRequestId`

业务保证：

- 不重复扣试用次数
- 不重复调用模型
- 不重复落库成功记录

### 15.2 模型可用性与降级

大模型厂商不是 100% SLA，必须定义不可用时的处理策略。

要求：

- 模型超时或限流时，明确返回“服务忙，请稍后再试”
- 本次失败不扣试用次数
- 陪练模式可考虑降级为“知识库骨架直出”
- 严格批改模式不可伪造结果，宁可返回失败提示也不能给假批改

推荐兜底顺序：

1. 主模型重试
2. 备用模型切换
3. 陪练降级为知识库骨架
4. 批改返回稍后重试提示

当前状态：

- 重复请求幂等已实现
- 模型整体故障的多供应商自动切换未实现

## 16. 非功能需求

### 16.1 可扩展性

当前架构要求保持模块边界清晰：

- 小程序负责输入与展示
- 后端负责鉴权、业务编排、检索、扣次、落库
- 模型层负责生成
- 数据库存业务真相

这样后续新增功能时，不应因为改一个前端卡片就牵动整套后端逻辑。

优先保持可扩展的模块：

- 陪练模式扩展
- 批改输出结构扩展
- 知识库模板扩展
- 会员权益扩展
- 后续网页端复用

### 16.2 性能

- 首个状态尽快返回
- 普通单次任务应控制在用户可接受范围内
- 历史记录读取要稳定

### 16.3 安全

- 微信敏感凭证只在服务端
- 模型密钥只在服务端
- 输入输出都走内容安全检查
- 正式环境关闭本地鉴权 fallback

### 16.4 可观测性

不能只有健康检查。

至少要补以下指标：

- 模型调用成功率
- 模型调用平均耗时
- 单次输入 token / 输出 token
- 单次调用成本
- OCR 成功率
- 批改结构完整率
- 估分分布与误差分布
- 试用次数消耗情况
- 内容安全拦截次数

日志链路要求：

- 每次任务有 requestId / clientRequestId
- 可以追溯到用户、模式、题型、结果状态

## 21. 一句话结论

这套产品现在已经具备“可运行的正式产品骨架”，但公开上线不再只是工程问题，而是三笔账的问题：

- 商业成本能不能扛住
- 未成年人合规能不能过
- 严格批改到底准不准

这三项没有补齐前，不建议把它当成可大规模投放的正式产品发布。
